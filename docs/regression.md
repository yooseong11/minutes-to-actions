# 회귀 기록

더미 회의록 5건(`01`~`05`)을 배포된 `/api/extract`에 넣고,
`regression/answer-key.md`의 기대 동작과 대조한 기록입니다.

- 측정 대상: 배포본 (로컬 아님)
- 채점 단위: 정답지의 "함정" 한 줄 = 1점
- **만점 41** (01: 10 / 02: 8 / 03: 7 / 04: 8 / 05: 8) — 스키마 3차 기준
  - 5차까지는 **만점 31** (01: 8 / 02: 6 / 03: 5 / 04: 6 / 05: 6)이었습니다.
    6차부터 샘플마다 «안건 수»·«안건 묶음» 두 줄이 늘어 10점이 더해집니다.
    **척도가 달라 5차 이하와 6차 이상은 직접 비교되지 않습니다.**
    바꾼 이유는 `regression/answer-key.md`의 「왜 만점을 다시 짰나」에 있습니다.

## 돌리는 법

```bash
npm run regression                       # 배포본
npm run regression -- --base http://localhost:3000   # vercel dev
```

5건을 순서대로 넣고 응답 원본을 `regression/runs/<날짜-시각>/`에 남깁니다.
같은 폴더의 `summary.md`가 화면에 찍힌 요약과 같습니다.

**채점은 스크립트가 하지 않습니다.** `regression/answer-key.md`와 대조해 손으로 셉니다 —
이 프로젝트에서 제일 자주 틀리는 것이 "무엇을 항목으로 볼 것인가"이고,
그건 기계가 셀 수 있는 종류가 아닙니다.

기준일이 없을 때 쓰는 `fallbackDate`는 **2026-09-14로 고정**입니다.
오늘 날짜를 쓰면 `"이번 주 안에"`가 실행한 날마다 다르게 환산되어
회차끼리 비교가 안 됩니다.

스크립트가 `⚠ 구버전 배포입니다`를 찍으면 점수를 재지 말고 배포부터 하십시오.

> LLM 출력은 실행마다 흔들립니다. 아래 점수는 **1회 측정값**이며,
> ±1~2점은 개선/악화가 아니라 편차로 봐야 합니다.
> 항목 누락(추출 자체가 안 되는 것)이 특히 흔들립니다.

안건 수와 안건 묶음은 5개 샘플 모두 맞아 **10/10**입니다. 안건 요약에 원문에
없는 숫자·이름·날짜도 없었습니다. 즉 504를 없앤 뒤에도 4.5의 핵심 품질은
유지됐고, 기존 항목 점수는 모델 편차 범위 안에서 유지됐습니다.

4차를 건너뛴 이유: 재고 나면 바로 5차 변경이 프롬프트를 또 바꾸기 때문에
점수가 하루도 못 가서 무효가 됩니다.

**5차는 22 → 29로 7점 올랐습니다.** 다만 4차(기준일)와 5차(TPO·논의내용)가
한 번에 반영된 값이라, 어느 쪽이 얼마나 기여했는지는 이 측정으로 못 가릅니다.
3차의 남은 실패 6건 중 4건이 해결됐는데 그중 셋은 4·5차 변경과 직접 관계가
없는 항목입니다 — **모델 편차일 가능성을 배제할 수 없습니다.** 한 번 더 재면 압니다.

0차와 1차의 낙차가 큰 이유: 0차는 사람이 한 건씩 보며 채점했고,
1차부터는 API 응답 전체를 기계적으로 대조했습니다. 같은 척도가 아닙니다.

## 회차별 변경 내용

### 1차 → 2차

**코드** (`lib/date.ts`)
- `"이번 주 안에"`, `"다음 주까지"` 환산 추가 (그 주 일요일)
- 수식어 없는 요일이 지나갔으면 다음 주로 밂
  - `"화요일 오전"` (회의일 9/11 금) → 9/8 이었음 → **9/15**
  - `"이번 주 X요일"`은 기한이 아니라 지목이므로 과거여도 유지

**프롬프트** (`lib/prompt.ts`)
- 작업 순서를 4단계로 명시하고, 제외 판정을 항목화 **이전**으로 옮김
- 참석자 규칙 신설 — `nameRaw`에 소속 금지, 1인칭·제3자 제외
- 검토 사유 10종에 원문 예시 추가

결과: 03(2→4), 05(3→5)가 크게 올랐습니다.
**부작용 2건** — 01의 대조군(영수증→정다은)이 사라졌고,
02에서 `due_unparseable` 오탐이 생겼습니다.

### 2차 → 3차

남은 실패 5건이 전부 "AI에게 부탁하던 것"이어서, 부탁을 **검사**로 바꿨습니다.

**코드로 이동** (`lib/people.ts`, `lib/postprocess.ts`)
- `assigneeInQuote` — 담당자 이름이 `quote`에 없으면 AI가 다른 발화에서 끌어온 것
- `isFirstPerson` — 나/내가/저/제가 → `assignee_unknown`
- `hasUnclearAmount` — 숫자+천/백/만에 "원"이 없으면 `unit_unclear`
- 번복 접기 — 다른 항목의 `supersededQuote`와 같은 `quote`는 중복이므로 버림
- `CODE_OWNED` — AI가 붙인 사유 8종을 버리고 코드가 다시 판정

**프롬프트에서 제거**
- 검토 사유 10개 중 8개 삭제. AI가 판단하는 것은 `conditional`, `ambiguous_intent` 둘뿐
- `"단순 현황 보고"` 제외 되돌림 (01 대조군을 죽인 원인)
- `SYSTEM_PROMPT` 3,683자 → **2,828자** (개편 전 원본보다도 짧음)

결과: 합계는 23 → 22로 오히려 1점 내려갔습니다.
다만 **고친 것과 깨진 것이 다릅니다** — 아래 참조.

## 읽는 법

점수보다 **어디서 틀리는지**가 중요합니다. 세 회차를 통틀어:

- **코드가 맡은 일**(날짜 환산, 역산, 참석자 대조, 환각 탐지)은 한 번도 틀리지 않았습니다.
  환각(`rejected`)은 5개 샘플 × 3회 = 15회 실행에서 **0건**입니다.
- 틀린 것은 전부 **AI가 판단하는 칸**과 **무엇을 항목으로 볼 것인가**입니다.
- 프롬프트로 고쳐지는 것(지시가 불명확했던 것)과 안 고쳐지는 것(모델이 사람처럼
  추론하려는 것)이 갈립니다. 후자는 프롬프트를 조여도 잘 안 됩니다.

## 5차에서 새로 볼 것 (측정 시 확인)

3차까지의 채점표에는 없던 칸이 넷 늘었습니다. 정답지에 함정으로 올라 있지 않으므로
**점수에는 넣지 말고** 따로 봅니다. 함정으로 승격할지는 한 번 재보고 정합니다.

| 칸 | 볼 것 | 특히 |
|---|---|---|
| `meetingTimeRaw` | 날짜 줄에서 시각만 떼어오는가 | 01 `"10:00"` — 날짜와 같이 뭉쳐 오면 실패 |
| `meetingPlaceRaw` | 회의가 열린 장소인가 | 01 `"대회의실"`. 본문에 나온 다른 장소를 집어오면 실패 |
| `purposeRaw` | **지어내지 않는가** | 제목 줄이 없는 샘플에서 `null`이 나와야 정상 |
| `discussionSummary` | 항목을 재나열하지 않는가 | 결정·할 일을 그대로 옮겨 적으면 실패 |

`purposeRaw`와 `discussionSummary`는 **환각 탐지를 타지 않습니다.**
`rejected` 0건이어도 이 두 칸은 안전하다는 뜻이 아닙니다. 눈으로 읽어야 합니다.
